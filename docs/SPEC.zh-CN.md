## 1. 本文档的目的与读者

本文档回答一个问题：**`ldbg` 这个命令行工具到底要满足哪些需求，每条需求的判定标准是什么。**
它不描述代码结构（那是设计文档的职责），而是描述"必须做到什么"以及"怎么算做到了"。

预期读者有三类，本文档为三类读者都写了可直接使用的内容：

| 读者 | 关心的部分 | 使用方式 |
| --- | --- | --- |
| 接手或扩展本工具的开发工程师 | 第 4 章功能需求、第 5 章非功能需求、第 6 章命令契约 | 改动前先确认要动的是哪条需求；改动后按该需求的"验收标准"回归 |
| 集群管理员 / 运维工程师 | 第 3 章角色与场景、第 4 章 D 组与 E 组需求、第 6 章命令契约 | 判断本工具会对集群做哪些改动、需要哪些权限 |
| AI 编码代理（例如 Claude Code） | 第 5.4 节可驱动性要求、第 6 章命令契约（含完整 JSON 字段） | 依据 JSON 字段与退出码做分支决策，不解析给人看的文本 |

**写作约定**：本文档不使用缩写与省略写法。所有术语在第 2 章给出完整定义，正文中每条需求都写明
"需求是什么、为什么需要它、怎么验证它做到了"，避免读者需要去翻代码才能理解意图。

## 2. 术语表

| 术语 | 完整含义与说明 |
| --- | --- |
| **Kubernetes** | 容器编排系统。本文档中简称"集群"时，均指目标 Kubernetes 集群。 |
| **Telepresence** | 开源工具，能把集群中某个服务的流量转发到开发者本机。`ldbg` 是它的封装层。 |
| **traffic-manager** | Telepresence 安装在集群中的服务端组件，负责管理拦截会话。运行在 `ambassador` 命名空间。 |
| **traffic-agent** | Telepresence 注入到被拦截工作负载 Pod 中的边车容器，负责把入站流量转发到开发者本机。**它与 traffic-manager 使用同一个容器镜像。** |
| **全量拦截（global intercept / TCP intercept）** | Telepresence 免费版提供的拦截模式：目标服务的**全部**流量都转发到开发者本机，不做按请求头的分流。分流式拦截（personal intercept）需要付费授权。 |
| **Istio ambient 模式** | Istio 服务网格的无边车数据面模式，由节点上的 `ztunnel` 组件接管四层流量。 |
| **`istio.io/dataplane-mode=none`** | 打在工作负载 Pod 模板上的标签，表示该工作负载不参与 ambient 数据面。被拦截的工作负载必须打上它，否则 `ztunnel` 的流量重定向会与注入的 traffic-agent 争抢端口，导致集群内调用方收到连接被重置的错误。 |
| **气隙环境（air-gapped）** | 无法访问公网的网络环境。本项目中，**目标集群是气隙的，开发者笔记本不是**。 |
| **容器镜像归档（docker-archive）** | `docker save` 产生的 tar 包格式。`docker load`、`ctr images import`、`minikube image load`、`kind load image-archive` 都能读取该格式。 |
| **容器运行时（container runtime）** | 节点上真正运行容器的软件，本项目需要区分三种：`containerd`、`docker`、`cri-o`。三者加载镜像归档的命令互不相同。 |
| **`ctr`** | containerd 自带的命令行工具。加载镜像时**必须指定 `-n k8s.io` 命名空间**，否则 kubelet 看不到该镜像。 |
| **镜像仓库（registry）** | 存放容器镜像的服务，例如 Harbor。集群节点从仓库拉取镜像。 |
| **kubeconfig** | 描述如何连接 Kubernetes 集群的配置文件，包含集群地址、证书与凭证。 |
| **VictoriaLogs** | 日志存储服务，部署在集群的 `logging` 命名空间，是 `ldbg logs query` 的查询后端。 |
| **JSON envelope（统一 JSON 外壳）** | 本工具所有 `--json` 输出共用的顶层结构：`{ok, command, data, error, hint}`。 |
| **AI 编码代理（AI agent）** | 能自主执行命令行工具的程序，例如 Claude Code。本文档中提到"代理"时均指此类程序。其关键特征是：**没有终端（TTY），无法回答任何交互式提示。** |
| **TTY（终端）** | 可交互的终端设备。判断依据是标准输入是否连接到真实终端，而不是是否为字符设备——`/dev/null` 也是字符设备，但不能交互。 |

## 3. 角色与使用场景

### 3.1 角色

**角色一：应用开发工程师。** 在自己的笔记本（Windows 11 或 Ubuntu）上开发 Spring Boot 微服务。
他要在 IDE 里打断点，让远程集群里的真实流量打到断点上。他通常**没有集群管理员权限**，
但对自己服务所在的命名空间有读写权限。

**角色二：集群管理员 / 运维工程师。** 负责把 Telepresence 的服务端组件装进气隙集群，
并把容器镜像送进集群节点。他关心：工具会对集群做哪些改动、需要哪些权限、能否先看清楚再执行。

**角色三：AI 编码代理。** 代替开发工程师执行"接管服务 → 复现问题 → 查日志 → 改代码 → 验证 → 收尾"
这一整套流程。它的硬约束是：**没有终端，无法回答任何交互式提示；无法看到人类可读的排版输出，
只能依赖结构化数据做判断。**

### 3.2 端到端场景

**场景一：日常调试（开发工程师 + AI 编码代理）**

开发工程师在服务仓库里执行预检、连接集群、接管服务，然后在 IDE 里以同步下来的集群环境变量启动
应用并打断点。集群内的调用方发出的真实请求落到本机断点上。改完代码后重启本机进程即可验证，
不需要重新构建镜像、不需要重新部署。调试结束后必须执行收尾命令，把集群恢复原状。
AI 编码代理可以执行除"在 IDE 里打断点"以外的全部步骤。

**场景二：首次把工具引入一个气隙集群（集群管理员）**

管理员在一台**能上网**的机器上，把 Telepresence 服务端镜像打成一个 tar 包；把 tar 包带进气隙环境；
再把它送进集群——要么推送到内部镜像仓库、要么通过安全外壳协议（SSH）逐个节点导入；
最后安装 traffic-manager。整个过程中集群不访问公网。

**场景三：笔记本无法直连集群应用程序接口（开发工程师）**

开发工程师的笔记本不能直接访问集群的应用程序接口（API Server），只能通过安全外壳协议登录到集群节点。
工具需要提供把凭证取回本机并建立隧道的能力，使笔记本获得完整能力。

## 4. 功能需求

每条需求的格式统一为：**需求编号与标题 / 需求陈述 / 为什么需要 / 验收标准 / 实现状态**。

### 4.A 组：本地调试闭环

#### FR-A1　把远程服务的流量接管到本机

**需求陈述**：一条命令即可完成：解析目标工作负载、把它的集群环境变量导出到本地文件、确保隧道已建立、
必要时为它做 Istio ambient 豁免、建立全量拦截。

**为什么需要**：这是整个工具存在的理由。手工完成这四步既繁琐又容易出错，尤其是 ambient 豁免这一步
——不做的话表现为集群调用方随机收到连接重置，排查成本极高。

**验收标准**：
1. 执行 `ldbg up <服务名> -n <命名空间>` 后，从集群内部发起的请求由本机进程应答。
2. 本地生成的环境变量文件包含该工作负载的 `env`、`envFrom` 以及其引用的 ConfigMap 与 Secret 的全部键值。
3. 如果目标命名空间启用了 ambient，工作负载的 Pod 模板上出现 `istio.io/dataplane-mode=none`，
   并带有 `ldbg` 自己的标记注解，供收尾时精确还原。

**实现状态**：已实现（`ldbg up`）。在 minikube 配合 Istio ambient 1.30 与 Telepresence 2.29.0 上验证通过。

#### FR-A2　目标解析必须符合开发者的心智模型

**需求陈述**：命令行上给出的名字**先按 Kubernetes Service 解析**，通过它的选择器找到背后的工作负载；
只有找不到同名 Service 时，才按同名的 Deployment、StatefulSet、DaemonSet 直接解析。

**为什么需要**：开发者说"我要调 gde-adapter"时，脑子里想的是别人调用的那个服务名，而不是工作负载对象名。
两者常常同名，但当它们不同名时，按 Service 解析才是符合直觉的行为。

**验收标准**：Service 与 Deployment 同名时任选其一都能工作；只有 Deployment 没有 Service 时也能工作；
两者都没有时给出明确报错，指出在哪个命名空间找不到哪个名字。

**实现状态**：已实现（`internal/k8s` 的工作负载解析逻辑）。

#### FR-A3　本地进程的端口由集群决定，并可覆盖

**需求陈述**：本机监听端口默认取自目标 Service 的第一个端口；允许通过参数指定"本机端口:集群端口"的映射。

**为什么需要**：默认值让常见情况零配置。可覆盖是必需的，因为存在两种真实情况：本机端口已被占用；
集群端口小于 1024，而 Linux 上非特权进程不能绑定这类端口。

**验收标准**：不指定端口时，输出中明确写出本机应监听的端口号；指定 `--port 18080:8080` 时按指定值生效。

**实现状态**：已实现。

#### FR-A4　收尾必须把集群恢复原状

**需求陈述**：一条命令完成：退出拦截、卸载注入的 traffic-agent、还原 ambient 豁免、断开隧道、清理本地生成文件。
顺序必须是"先卸载 agent、再还原 ambient"。

**为什么需要**：顺序反了会造成故障——工作负载回到 ambient 网格时如果 traffic-agent 还在，端口会被黑洞，
服务对整个集群不可用。另外，如果 agent 卸载失败，工具必须**保留** ambient 豁免（宁可让工作负载留在网格外，
也不能让它不可用），并明确告诉使用者需要人工做什么。

**验收标准**：收尾后工作负载的 Pod 模板上不再有 `dataplane-mode` 标签与 `ldbg` 注解；
agent 卸载失败时输出明确保留说明与人工修复命令。

**实现状态**：已实现（`ldbg down`）。

#### FR-A5　接管效果必须能从集群内部证明

**需求陈述**：提供一条命令，在**集群内部**创建一个临时 Pod 向目标服务发起请求，并展示是谁应答的。

**为什么需要**：从笔记本上发起的请求可能根本没走集群路径，证明不了拦截生效。只有来自集群内部的请求才是有效证据。

**验收标准**：拦截生效时，返回内容来自本机进程；命令同时返回结构化的成功标志与退出码。
在不允许创建 Pod 的命名空间（例如受准入控制限制的 `kube-system`）中该命令可能失败，
此时文档必须提供替代验证方式，且不得把这种失败描述为"拦截失败"。

**实现状态**：已实现（`ldbg test`）。替代验证方式已写入操作指南。

### 4.B 组：日志

#### FR-B1　历史日志查询

**需求陈述**：能按服务名、Pod 名、容器名、节点名、日志级别、关键字查询集群日志存储中的日志，
支持相对时间窗口（例如 5 分钟、30 分钟、1 小时、4 小时、12 小时、1 天、2 天、7 天）与绝对时间区间。

**为什么需要**：调试的第一步通常是"这个异常以前发生过吗"，而被删除的 Pod 的日志用 `kubectl logs` 已经查不到。

**验收标准**：能查到已被删除 Pod 的历史日志；关键字支持多词与整体短语；结果超出上限时明确告知已截断并给出收窄建议。

**实现状态**：已实现（`ldbg logs query`、`logs tail`、`logs stats`、`logs fields`、`logs values`）。

#### FR-B2　拦截期间的本地日志查询

**需求陈述**：拦截期间，本机进程的日志必须可用同一套过滤词汇查询。

**为什么需要**：拦截期间集群侧对该服务是空窗——流量都在本机，集群里没有新日志。
如果此时只能查集群日志，等于调试最关键的时段没有日志可看。

**验收标准**：无论应用是由 IDE 启动还是由工具启动，本机日志都能被查询到；
Java 异常堆栈必须归并为一条记录，关键字能匹配到堆栈帧。

**实现状态**：已实现（`ldbg logs local`）。工具默认向环境变量文件注入日志落盘变量，并对自己启动的进程做输出复制。

### 4.C 组：远程接入

#### FR-C1　笔记本没有 kubeconfig 时的接入能力

**需求陈述**：当笔记本无法直连集群应用程序接口、但能通过安全外壳协议登录集群节点时，
工具必须能把节点上可用的凭证取回本机，并改写为经由本地隧道端口访问。

**为什么需要**：Telepresence 基于 Kubernetes 官方客户端库实现，**没有 kubeconfig 就完全无法工作**，
不存在"用裸 kubectl 代替"的方案。因此把凭证取回来是唯一出路。

**验收标准**：
1. 取回的 kubeconfig 是自包含的（所有证书内联，不引用节点上的文件路径）。
2. 改写后**保留完整的传输层安全校验**：服务器地址改为本地端口，同时把校验用的服务器名固定为原始地址
   ——因为集群证书不是签给 `127.0.0.1` 的，直接跳过校验是不必要的降级。
3. 文件以仅属主可读写的权限写出，**内容绝不打印到标准输出**。

**实现状态**：已实现（`ldbg cluster fetch-kubeconfig`，v0.2.1）。

#### FR-C2　桥接能力的逐项验证

**需求陈述**：提供命令，分级检查经隧道或代理的集群连接分别支持到什么程度：
应用程序接口可达性、命名空间读权限、端口转发（是否承载流升级）、日志存储可达性。

**为什么需要**："这条链路能不能用"不能靠假设。实测发现 `kubectl proxy` 是能承载端口转发的
（与常见说法相反），但是否可用取决于版本与链路中是否还有其它代理，所以必须逐环境验证。

**验收标准**：每项独立给出通过或失败，失败项附带可执行的下一步建议；聚合结论同时体现在退出码与结构化字段中。

**实现状态**：已实现（`ldbg cluster probe`，v0.2.0）。

### 4.D 组：离线镜像交付（打包侧）

#### FR-D1　打包不得依赖本机安装 Docker

**需求陈述**：把 Telepresence 服务端镜像打成传输用的 tar 包这一步，**不得要求本机安装 Docker 或任何容器工具**。

**为什么需要**：实际使用中，开发工程师在一台全新的 Windows 11 笔记本上执行这一步，机器上没有 Docker，
也不应为了打一个包去装一整套容器环境。

**验收标准**：在没有任何容器工具的机器上执行打包命令能成功产出 tar 包；
该 tar 包能被 `docker load`、`ctr images import`、`minikube image load` 正常读取。

**实现状态**：已实现（`ldbg bundle`，v0.3.0）。工具内置了直接与镜像仓库通信的能力。
若本机恰好有 Docker 且镜像已在本地，则直接使用本地镜像打包，全程不联网。

#### FR-D2　打包目标架构由集群决定，且必须显式

**需求陈述**：tar 包的目标处理器架构默认为 `linux/amd64`，可通过参数改为 `linux/arm64` 等；
**一个 tar 包只包含一种架构**；实际打包的架构必须在输出中写明。

**为什么需要**：这个包是给**集群**用的，不是给构建它的机器用的。如果默认跟随本机架构，
在 Apple 芯片的 Mac 上会静默产出 arm64 包，导入 amd64 集群后表现为容器启动时的可执行文件格式错误，
排查成本很高。限制为一包一架构，是为了让所有导入方式（`docker load`、节点导入、仓库推送）行为一致可预期。

**验收标准**：默认产出 amd64 包；指定 arm64 时产出的包经 `docker load` 后确认架构为 `arm64`；
未显式指定输出文件名时，非默认架构的文件名自动带上架构后缀，避免两次打包互相覆盖；
传入逗号分隔的多架构时明确报错并说明应分两次执行。

**实现状态**：已实现（v0.3.0）。已对真实镜像仓库验证：请求 arm64 时取回的镜像配置确为 arm64，
且与 amd64 的内容摘要不同。

#### FR-D3　镜像源可替换

**需求陈述**：当官方镜像仓库不可达时，允许从内部仓库或镜像站拉取；**产出的 tar 包仍以官方镜像名标记**。

**为什么需要**：目标网络环境中官方仓库长期不稳定。产出物保持官方名，是为了让集群侧的安装步骤完全不用改动。

**验收标准**：指定替换源后能成功产出 tar 包；`docker load` 回来的镜像名是官方名而非替换源的名字；
支持为私有仓库提供凭证，支持自签名证书的仓库。

**实现状态**：已实现（v0.3.0）。已用一个小体积镜像做过完整回环验证。

#### FR-D4　代理支持，且必须能自动发现 Windows 系统代理

**需求陈述**：拉取镜像时按以下优先级使用代理：命令行参数、环境变量、**Windows 系统代理设置**、直连。
实际生效的代理必须在每次拉取时打印出来。

**为什么需要**：这是实际踩到的问题。Go 语言标准库只读环境变量，**不读 Windows 的系统代理设置**。
而 Clash、v2rayN 这类工具正是配置系统代理——于是浏览器能上网，本工具却直连被拦截，
报错还只是一句连接超时，使用者完全看不出"我明明开着代理"和"工具没在用它"之间的关系。

**验收标准**：设置了环境变量时使用环境变量；未设置但 Windows 注册表中有系统代理时自动使用它；
输出中始终写明本次使用的代理及其来源，**密码必须打码**；配置的是自动配置脚本（PAC）时明确提示无法解析并给出替代方案。

**实现状态**：已实现（v0.3.2）。

#### FR-D5　需要认证的代理必须能用

**需求陈述**：为代理提供凭证的方式必须是独立参数，而不是要求把凭证拼进代理地址。

**为什么需要**：两个原因。第一，**Windows 注册表里只有代理地址，没有账号密码**（凭证在凭据管理器中，程序取不到），
所以自动发现出来的代理是"裸"的，遇到需要认证的代理必然被拒绝。第二，把凭证拼进地址在密码含有
`@`、`/`、`:` 等字符时会被静默解析错误——主机名都会变，且不报错。

**验收标准**：使用独立参数提供凭证后，含特殊字符的密码能正常工作且主机名不被破坏；
代理返回"需要代理认证"时，提示必须指向代理凭证参数，而不是指向镜像仓库的凭证参数；
密码不得出现在任何输出中。

**实现状态**：已实现（v0.3.2）。已用一个强制要求认证的本地代理做过端到端验证，密码含 `@ : / #`。

### 4.E 组：集群侧导入与安装

#### FR-E1　节点容器运行时必须自动识别

**需求陈述**：把镜像导入节点时，所用命令必须与该节点的容器运行时匹配，且**不得要求使用者手工指定**。

**为什么需要**：三种运行时的加载命令互不通用，选错就失败。而集群本身已经把答案记录在节点状态里，
让使用者去查再手工填写是没有必要的负担，也是一处容易出错的地方。

**验收标准**：
1. 从集群读取每个节点的运行时，并据此选择命令：
   containerd 使用 `ctr -n k8s.io images import`，docker 使用 `docker load`，cri-o 使用 `podman load`。
2. **containerd 必须导入 `k8s.io` 命名空间**。导入到默认命名空间会"成功"，但 kubelet 看不到该镜像
   ——这是一个不报错的静默失败，必须从根本上避免。
3. k3s 与 RKE2 内嵌 containerd 且没有独立的 `ctr` 命令，因此需在节点上按顺序探测可用命令。
4. 识别不出运行时时的处理见 FR-E7（节点上探测实际引擎，或由使用者强制指定）。

**实现状态**：已实现（v0.3.3）。docker 路径已在真实节点验证；containerd 与 cri-o 路径目前仅有单元测试覆盖。

#### FR-E2　默认导入到全部可调度节点

**需求陈述**：默认把镜像导入集群中**所有可调度节点**；允许缩小范围；未完全覆盖时必须明确警告。

**为什么需要**：traffic-manager 只有一个副本，但**注入的 traffic-agent 使用同一个镜像**，
并且会跟随被拦截的工作负载调度到任意节点。少导一个节点，就意味着某次拦截时 Pod 恰好调度到那个节点，
表现为镜像拉取失败——而集群是气隙的，拉不到就是拉不到。

**验收标准**：不指定节点时导入全部可调度节点（被隔离的节点与带有人为调度限制的节点排除在外）；
未覆盖全部可调度节点时输出警告，并在结构化输出中以布尔字段体现。

**实现状态**：已实现（v0.3.3）。

#### FR-E3　两条导入路径

**需求陈述**：提供两条把镜像送进集群的路径，并能自动选择：
（一）推送到内部镜像仓库，由各节点自行拉取；（二）通过安全外壳协议逐节点传输并导入。
自动选择的规则必须保守：**不得在没有明确信号的情况下自行登录集群节点**。

**为什么需要**：有内部仓库时，仓库路径最干净、最容易扩展到多节点；没有仓库时，逐节点导入是唯一可行方式。
而登录共享集群的每一个节点是有影响面的操作，不是可以"推断"出来的意图。

**验收标准**：给出仓库地址时走仓库；给出登录用户或节点列表时走逐节点；识别出单节点开发集群时用该集群自带的加载命令；
以上都不满足时**停下来说明三条路径各自需要什么**，而不是猜一个执行。
仓库推送同样不得要求本机安装 Docker。

**实现状态**：已实现（v0.3.3）。仓库推送已通过"推送后拉回比对内容摘要"验证。

#### FR-E4　逐节点导入必须完整且可诊断

**需求陈述**：每个节点的处理流程是：传输 → 导入 → **校验镜像确实可见** → 清理节点上的临时文件。
单个节点失败不得中断其余节点，最终必须给出逐节点的结果汇总。

**为什么需要**：只做"导入"而不做"校验"，无法区分"命令返回成功"与"kubelet 真的能看到镜像"
——前面提到的 containerd 命名空间问题正是这种情况。临时文件不清理会在节点上堆积数十兆的垃圾。
而多节点场景下，一个节点不可达就放弃全部工作是不可接受的。

**验收标准**：结构化输出中每个节点独立给出传输、导入、校验、跳过四个状态与错误原因；
一个节点失败时其余节点继续执行；节点上的临时文件在成功与失败路径下都被清理（除非显式要求保留）。

**实现状态**：已实现（v0.3.3、v0.3.4）。三节点场景中人为让中间一个节点失败，已验证其余节点继续且汇总正确。

#### FR-E5　执行前可审阅

**需求陈述**：提供一种模式，逐节点打印**将要在节点上执行的确切命令**，但不做任何改动。

**为什么需要**：这是对共享集群节点执行特权命令，管理员有权在执行前看清楚内容。
对 AI 代理而言，这也是把计划摊给人类确认的方式。

**验收标准**：该模式下不产生任何远程连接与文件改动（可通过外部记录验证）；打印的命令与实际执行的命令一致。

**实现状态**：已实现（`--dry-run`，v0.3.3）。已通过外部记录验证该模式下零执行。

#### FR-E6　重复执行必须安全

**需求陈述**：重复执行安装命令不得失败。已安装的组件应转为升级；已存在的镜像可选择跳过。

**为什么需要**：真实运维中重复执行很常见（新增节点、更换仓库）；AI 代理在遇到不确定情况时也会重试。
一个"已安装"就硬报错的命令，会让代理的重试必然失败。

**验收标准**：对已安装 traffic-manager 的集群再次执行安装命令能成功完成。

**实现状态**：已实现（v0.3.3）。

#### FR-E7　kubelet 上报非标准运行时字符串时不得直接放弃

**需求陈述**：kubelet 在节点状态中上报的 `containerRuntimeVersion` 不是标准形式
（标准形式为 `docker://版本号`、`containerd://版本号`、`cri-o://版本号`）时，
逐节点导入不得直接失败。必须同时提供三个出口：
（一）使用者用参数强制指定运行时（`--runtime docker|containerd|cri-o`）；
（二）不给任何参数时，通过安全外壳协议**在节点上探测**实际安装的容器引擎，
用命中的引擎完成导入与校验；
（三）自定义加载命令兜底（`--import-cmd`，原有能力）。
无论走哪条路，kubelet 上报的**原始字符串必须展示给使用者**，不得只显示"未知"。

**为什么需要**：这是一次真实故障（2026-08-04）：某定制化平台即服务（PaaS）集群的节点
（节点名形如 `paas-172-25-71-121`）实际运行 docker，但 kubelet 上报的运行时字符串不是
`docker://…` 的标准形式，导致工具在**已经能通过安全外壳协议登录节点**的情况下，
仅因为解析不出运行时就拒绝执行，且报错里丢弃了原始字符串，使用者无从诊断。
既然节点可登录，探测实际引擎的成本只是一条远程命令，直接放弃是错误的默认行为。

**验收标准**：
1. `--runtime` 只接受三个已知运行时取值，拼写错误立刻报错（不得静默落入探测）；
   强制指定后保留逐节点校验。
2. 探测在**一次连接**内完成（探测 → 导入 → 校验 → 清理），探测顺序为
   docker → ctr → k3s ctr → nerdctl → podman → isula——docker 排最前，
   因为非标准字符串绝大多数来自改名的 docker 分支，而独立部署的 containerd 与 cri-o
   会正常上报标准形式；containerd 分支仍必须使用 `k8s.io` 命名空间。
3. 探测结果在人类输出与结构化输出中都要标注（形如 `docker (probed)`），
   节点上没有任何已知引擎时明确列出探测过的命令清单。
4. 预检命令（`cluster preflight`）对识别不出的运行时展示 kubelet 原文并提示 `--runtime`。
5. 通过 `--nodes` 手工给出的、不在集群节点列表里的地址**不参与探测**
   （可能是拼写错误，把镜像装进错误的机器不可接受）——此时仍要求
   `--runtime` 或 `--import-cmd` 之一。

**实现状态**：已实现（v0.3.5）。探测脚本已在真实 docker 节点上验证
（探测命中、导入、校验、清理、skip-present 全部通过）；`--runtime` 强制路径已全链路验证。

#### FR-E8　安装参数必须与 traffic-manager chart 的取值定义一致

**需求陈述**：以内嵌 chart 安装 traffic-manager 时，下发的取值名必须与该 chart 实际声明的取值一致；
并且 traffic-manager 镜像与**注入的 traffic-agent 镜像**都必须指向已侧载或已推送的位置。

**为什么需要**：这是一次真实故障（2026-08-05）。工具下发的是 `images.registry`、
`images.agentImage`、`images.pullPolicy`——这是旧版 chart 的取值名。
`telepresence-oss` chart（2.29.0）没有顶层 `images` 键，且其取值定义中
"不允许出现未声明的属性"，因此**整批取值在校验阶段被拒绝，安装一步都没有执行**，
报错为 `additional properties 'images' not allowed`。当时镜像其实已经成功导入节点，
故障点完全在安装参数上。

同一处还有第二个隐患：注入的 traffic-agent 镜像是由**被拦截工作负载的 Pod** 去拉取的。
指定了内部镜像仓库时，如果 agent 镜像仍指向公网地址，安装会显示成功，
而失败要等到真正发起拦截时才以镜像拉取失败的形式出现——在气隙集群中即为不可恢复。

**验收标准**：
1. traffic-manager 镜像通过 `image.registry`、`image.pullPolicy` 下发；
   注入的 traffic-agent 镜像通过 `agent.image.registry`、`agent.image.name`、
   `agent.image.tag`、`agent.image.pullPolicy` 下发（chart 要求镜像引用**拆成三段**）。
2. 完整镜像引用拆分时，仓库地址允许带端口（形如 `主机:5000/路径/名称:标签`），
   即只有最后一段路径里的冒号才是标签分隔符。
3. 以摘要（digest）固定的镜像引用**明确报错**，因为 chart 只能表达"仓库/名称:标签"。
4. 指定内部镜像仓库且未显式指定 agent 镜像时，agent 镜像**自动指向该仓库**。
5. 单元测试固定这些取值名，并断言不再出现任何 `images.` 前缀的取值。

**实现状态**：已实现（v0.3.6）。已在真实集群上完成**完整安装链路**验证：
卸载 traffic-manager 后重新执行完整的 `cluster install`（不加 `--import-only`），
安装成功、Pod 就绪，且渲染结果正确（manager 镜像与拉取策略、agent 镜像的三个环境变量）；
重复执行走升级路径同样成功。

> **本次故障暴露的验证缺口（值得记录）**：此前对 `cluster install` 的真机验证一直加着
> `--import-only`，只覆盖了镜像分发那一半；而验证集群上的 traffic-manager 是用原生
> telepresence 命令装的，因此安装参数错误长期未被发现。
> **凡是命令分成两段的，验证必须覆盖到最后一段。**

### 4.F 组：面向 AI 编码代理的可驱动性

#### FR-F1　统一的结构化输出

**需求陈述**：所有命令支持 `--json`，输出统一外壳 `{ok, command, data, error, hint}`。
`ok` 表示命令本身是否执行成功；对于会做多项检查的命令，聚合结论放在 `data.ok` 中。

**为什么需要**：代理必须能在不理解每个命令输出格式的前提下做出"成功还是失败、下一步做什么"的判断。

**验收标准**：失败时 `error` 与 `hint` 均有值且退出码非零；`data.truncated` 为真时 `hint` 给出收窄建议。

**实现状态**：已实现。

#### FR-F2　命令不得因等待交互而挂起

**需求陈述**：在没有终端的环境中执行时，任何需要人工输入的操作都必须**立即失败并给出明确原因**，
而不是无限期等待。远程连接必须有超时上限。

**为什么需要**：这是代理场景下最严重的失败模式。代理没有终端，安全外壳协议的密码提示既看不到也答不了，
结果是命令永久挂起，代理被卡死。实测中，一个不可达节点在没有超时设置时会阻塞 2 分 16 秒。

**验收标准**：无终端时自动启用批处理模式并设置连接超时；不可达节点在数秒内报错
（实测由 2 分 16 秒降至 5.0 秒）；提供显式参数以便人类使用者恢复交互式行为。

**注意**：判断是否有终端必须使用真正的终端检测。仅检查"是否为字符设备"是错误的，
因为 `/dev/null` 也是字符设备——这个错误会让代理被判定为交互式环境，从而使上述保护完全失效。

**实现状态**：已实现（v0.3.4）。

#### FR-F3　密码类凭证只能经环境变量传入

**需求陈述**：节点登录密码只能通过环境变量 `LDBG_SSH_PASSWORD` 提供，**不提供命令行参数**。

**为什么需要**：命令行参数会出现在进程列表、命令历史与持续集成日志中。
同时，由于操作系统自带的安全外壳客户端只从终端读取密码，代理场景下必须由本工具自己实现协议才能使用密码
——这也是工具内置安全外壳传输层的唯一理由。

**验收标准**：设置该环境变量后，在无终端环境中能完成节点登录与镜像导入；
每个节点只进行一次认证；密码不出现在任何输出中。

**实现状态**：已实现（v0.3.4）。已用一个仅接受密码认证的服务端做过端到端验证，
密码含 `@ : / #` 等特殊字符，上传内容经内容摘要比对完全一致。

#### FR-F4　网络往返次数最小化

**需求陈述**：单个节点的处理应尽量减少连接次数，同时**不得因此丢失阶段级的诊断信息**。

**为什么需要**：连接次数直接决定延迟；在使用密码认证且由人类操作时，它还直接决定要输入几次密码。
但如果为了减少连接而把多个步骤合并成"一个成功或失败"，就无法区分是导入失败还是校验失败，
这在排查上是明显的倒退。

**验收标准**：单节点连接次数由四次降为两次；同时结构化输出仍能分别体现导入与校验的结果。

**实现状态**：已实现（v0.3.4）。导入、校验、清理合并为一条远程脚本，通过回传各阶段退出码保留诊断能力。

### 4.G 组：安全与凭证处理

#### FR-G1　凭证不落入日志与标准输出

**需求陈述**：所有凭证类信息（集群 kubeconfig 内容、镜像仓库密码、代理密码、节点登录密码、
以及从集群同步下来的 Secret 值）都不得出现在标准输出、错误输出与结构化输出中。

**为什么需要**：这些输出会被复制粘贴进工单、被持续集成系统采集、被 AI 代理纳入上下文。

**验收标准**：同步集群环境变量时，Secret 值在终端输出中打码，但完整写入权限受限的本地文件；
代理地址在展示时密码位置被替换；取回的 kubeconfig 内容不打印。

**实现状态**：已实现。其中代理密码打码是在 v0.3.2 修复的——首个实现直接输出了完整地址，含明文密码。

#### FR-G2　主机密钥校验不得静默降级

**需求陈述**：使用内置安全外壳传输层时，若目标主机已记录在本机的已知主机文件中而密钥不匹配，
必须**直接拒绝连接**；若该主机尚未记录，则打印指纹并在本次运行中接受，同时提供严格模式参数。

**为什么需要**：密钥不匹配是中间人攻击的典型信号，这是必须保留的防护。
而气隙集群的节点通常从未出现在开发者笔记本的已知主机文件中，若一律拒绝会导致功能不可用。

**验收标准**：已记录且不匹配时报错并终止；未记录时输出指纹并继续；严格模式下未记录也终止。

**实现状态**：已实现（v0.3.4）。

#### FR-G3　最小权限与降级

**需求陈述**：读取集群节点列表等较高权限操作失败时，功能应降级而不是整体失败。

**为什么需要**：开发工程师的凭证通常没有列出节点的权限，但这不应妨碍他使用与自己命名空间相关的功能。

**验收标准**：无节点列表权限时，架构建议与逐节点表格降级为提示"请手工指定"，其余功能不受影响。

**实现状态**：已实现。

## 5. 非功能需求

### 5.1 运行环境

工具必须是**单文件可执行程序、无需运行时依赖**，可在 Ubuntu、Windows 11 与 macOS（Apple 芯片）上原生运行。
构建时不使用 C 语言互操作，以保证交叉编译产物可直接使用。Go 语言版本基线为 1.22。

**约束记录**：引入第三方库时必须确认其声明的 Go 版本不高于 1.22，否则会顶掉本基线。
实际发生过一次：容器镜像库的较新版本要求 Go 1.23 乃至 1.25，因此固定在满足条件的版本上。

### 5.2 离线能力

集群侧全流程不得访问公网。开发者笔记本可以联网。构建本工具本身需要一次性联网拉取依赖，之后可离线构建。

### 5.3 跨平台一致性

所有命令在三个平台上行为一致。平台差异（提权方式、路径分隔符、环境变量设置语法、构建包装脚本名）
必须在文档中并列写出，不得只写一个平台的写法。

**约束记录**：错误信息的匹配逻辑必须覆盖 Windows 的表述。实际发生过一次：网络错误分类只匹配了
类 Unix 系统的措辞，导致 Windows 上所有网络故障都落入"未知"分类，给出的建议毫无意义。

### 5.4 AI 编码代理可驱动性

除以下两项外，全部流程必须可由代理在无人值守下完成：

1. **Telepresence 建立网络守护进程需要一次性提权**（Linux 上是超级用户权限，Windows 上是用户账户控制确认）。
   这一步必须由人类执行，工具在检测到未连接时应明确提示。
2. **在集成开发环境中打断点与单步调试**属于人类工作。

其余所有命令都必须满足：支持结构化输出、有意义的退出码、不因等待交互而挂起、可先审后执行。

### 5.5 可维护性

面向使用者的文本使用英文（与现有代码保持一致），面向使用者的文档使用简体中文。
纯逻辑（命令拼装、错误分类、路径与地址解析、覆盖面计算）必须与副作用分离，以便单元测试覆盖。
所有涉及外部命令的行为，必须能用替身程序做确定性验证。

## 6. 命令契约

本章给出每个命令的输入、输出与退出码。**结构化输出的字段名以本章为准。**

### 6.1 通用约定

**全局参数**（所有命令可用）：

| 参数 | 含义 |
| --- | --- |
| `--json` | 输出统一外壳的结构化结果 |
| `--kubeconfig <路径>` | 指定 kubeconfig 文件，默认取 `KUBECONFIG` 环境变量，再默认取用户主目录下的 `.kube/config` |
| `--context <名称>` | 指定 kube 上下文，默认使用当前上下文 |
| `-n, --namespace <名称>` | 目标命名空间 |
| `--telepresence-bin <路径>` | 指定 telepresence 可执行文件位置 |

**统一外壳**：

```json
{ "ok": true, "command": "status", "data": { }, "error": "", "hint": "" }
```

`ok` 为命令本身是否执行成功。失败时 `data` 省略，`error` 与 `hint` 有值，进程退出码为 1。
`doctor` 与 `cluster probe` 另有 `data.ok` 表示各项检查的聚合结论，聚合失败时退出码同样为 1。
**两个 `ok` 含义不同，不可混用。**

### 6.2 调试闭环命令

| 命令 | 关键参数 | `data` 主要字段 |
| --- | --- | --- |
| `ldbg up <服务>` | `--port 本机:集群`、`--run`（可重复，指定启动本机应用的命令）、`--env-out`、`--keep-ambient`、`--no-local-log`、`--run-config intellij\|vscode` | `target`、`namespace`、`envFile`、`varsWritten`、`localLogFile`、`port`、`localPort`、`connected`、`interceptActive`、`launched`、`ambient`、`ambientOptOutApplied` |
| `ldbg down` | `--stay-connected`、`--keep-files` | `leftIntercepts`、`uninstalledAgents`、`revertedAmbient`、`keptAmbientOptOut`、`disconnected`、`removedFiles` |
| `ldbg status` | 无 | `telepresenceFound`、`connected`、`kubeContext`、`namespace`、`interceptActive`、`intercepts`、`managerInstalled`、`clusterReachable`、`clusterVersion`、`hint` |
| `ldbg doctor [服务]` | 无 | `checks`（每项含 `name`、`status`（`pass`/`warn`/`fail`）、`detail`）、`ok` |
| `ldbg sync <服务>` | `--env-out`、`--run-config`、`--no-local-log` | `target`、`namespace`、`kind`、`container`、`envFile`、`written`、`skipped`、`localLogFile`、`vars` |
| `ldbg test <服务>` | `--path`、`--port` | `url`、`fromClusterOrigin`、`succeeded`、`exitCode`、`body` |

### 6.3 日志命令

`ldbg logs query`、`logs tail`、`logs stats`、`logs local`、`logs fields`、`logs values`、
以及直接读取 Pod 日志的 `ldbg logs <服务>`。

共用过滤参数：`--service`、`--pod`、`-c/--container`、`--node`、`--level`、`-q/--query`、`-i/--ignore-case`；
时间参数：`--since`（相对窗口）、`--from`/`--to`（绝对时间）；
后端地址：`--vlogs-addr`、`--vlogs-namespace`。

地址解析优先级：命令行参数、`VLOGS_ADDR` 环境变量、经 telepresence 隧道直连集群内服务地址、自动端口转发。

### 6.4 `ldbg bundle`（打包）

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--tp-version` | `2.29.0` | Telepresence 版本，决定镜像标签 |
| `--platform` | `linux/amd64` | 目标架构，格式为"操作系统/架构[/变体]"，**只接受单个值** |
| `--out` | `tel2-bundle.tar` | 输出文件；未显式指定且架构非默认时自动带上架构后缀 |
| `--engine` | `auto` | `auto`（本机有 Docker 且镜像已在本地则用 Docker，否则内置拉取）、`native`（内置拉取）、`docker` |
| `--from` | 空 | 替换拉取源，可为仓库前缀或完整镜像引用 |
| `--creds` | 空 | 镜像仓库凭证，格式为"用户名:密码" |
| `--insecure` | 关闭 | 允许明文传输或自签名证书的仓库 |
| `--proxy` | 空 | 代理地址 |
| `--proxy-creds` | 空 | 代理凭证，格式为"用户名:密码" |
| `--force-pull` | 关闭 | 本地已有镜像时仍重新拉取 |
| `--no-pull` | 关闭 | 不拉取，直接使用本机 Docker 中已有的镜像 |

`data` 字段：`image`、`tarball`、`platform`、`engine`、`source`、`pulled`、`skippedPull`、`sizeBytes`、
`proxy`（已打码）、`proxySource`。

### 6.5 `ldbg cluster preflight`（集群预检）

`data` 字段：`kubernetesVersion`、`image`、`importVia`、
`nodes`（每项含 `name`、`internalIP`、`arch`、`os`、`runtime`、`runtimeVersion`、`providerID`、`schedulable`）、
`nodeArchitectures`、`nodeRuntimes`、`bundlePlatform`。

### 6.6 `ldbg cluster install`（导入并安装）

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--bundle` | `tel2-bundle.tar` | 打包命令产出的文件 |
| `--import-via` | `auto` | `auto`、`registry`、`ssh`、`minikube`、`kind`、`k3d`、`ctr` |
| `--registry` | 空 | 内部镜像仓库地址；给出即选择仓库路径 |
| `--ssh-user` | 空 | 节点登录用户；给出即选择逐节点路径 |
| `--nodes` | 空 | 手工指定节点地址列表，覆盖自动发现 |
| `--ssh-opts` | 空 | 透传给系统安全外壳客户端的额外参数 |
| `--ssh-transport` | `auto` | `auto`（设置了密码环境变量则用内置传输层）、`system`、`native` |
| `--ssh-port` | `22` | 内置传输层使用的端口 |
| `--ssh-key` | 空 | 内置传输层使用的私钥文件 |
| `--ssh-strict-host-key` | 关闭 | 要求目标主机已记录在已知主机文件中 |
| `--ssh-timeout` | `10` | 连接超时秒数 |
| `--interactive` | 关闭 | 允许交互提示；默认在无终端时关闭 |
| `--sudo` | 开启 | 节点上的加载命令使用超级用户权限执行 |
| `--remote-tmp` | `/tmp` | 节点上暂存归档的目录 |
| `--runtime` | 空 | 强制指定全部节点的容器运行时（`docker`、`containerd`、`cri-o` 之一）；不指定时从集群读取，识别不出则在节点上探测（见 FR-E7） |
| `--import-cmd` | 空 | 自定义加载命令，其中 `%s` 会被替换为归档路径 |
| `--keep-remote` | 关闭 | 保留节点上的临时归档 |
| `--skip-present` | 关闭 | 镜像已存在的节点直接跳过 |
| `--dry-run` | 关闭 | 只打印将要执行的命令，不做任何改动 |
| `--import-only` | 关闭 | 只导入镜像，不安装 traffic-manager |
| `--no-import` | 关闭 | 跳过导入，只安装 traffic-manager |
| `--engine`、`--creds`、`--insecure`、`--proxy`、`--proxy-creds` | 同打包命令 | 仓库推送时使用 |

环境变量 `LDBG_SSH_PASSWORD`：节点登录密码。**这是提供密码的唯一方式。**

`data` 字段：`image`、`importVia`、`registry`、`agentImage`、`fullyCovered`、`dryRun`、`installed`、
`nodes`（每项含 `node`、`address`、`runtime`、`transport`、`transferred`、`imported`、`verified`、`skipped`、`commands`、`error`）。
其中 `runtime` 在探测路径下带有 ` (probed)` 后缀（例如 `docker (probed)`），
表示该值不是 kubelet 上报的，而是在节点上探测出来的。
